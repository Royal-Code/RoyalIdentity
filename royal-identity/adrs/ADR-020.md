# 020. Versionamento de payloads persistidos durante o pre-release

## 1. Contexto

Os stores Configuration e Operational persistem grafos não relacionais como JSON acompanhado por uma coluna de
versão. Os serializers aceitam somente a versão corrente e rejeitam JSON inválido, evitando materialização
parcial de configuração ou artefatos operacionais.

O RoyalIdentity ainda está em desenvolvimento, sem versão lançada, instalação de produção ou consumidor cujo
banco precise sobreviver a upgrades. Os ambientes executáveis atuais são testes, Demo/Aspire e instâncias de
desenvolvimento que podem ser reprovisionadas. Apesar disso, planos pré-release reservaram uma sequência de bumps
de payload v2, v3 e seguintes para cada alteração incompatível, como se já existisse um contrato persistido
publicado.

Essa sequência cria coordenação artificial entre planos, seeds e testes sem entregar compatibilidade útil: os
serializers continuam sem leitores legados ou upcasters, e os bancos de desenvolvimento precisam ser
reprovisionados de qualquer forma.

## 2. Decisão

Até o primeiro release ou outro marco explícito que passe a exigir upgrade de dados persistidos, todos os
payloads JSON internos dos stores Configuration e Operational permanecem na versão `1`.

- As colunas de versão, os serializers e a validação fail-closed permanecem. A arquitetura de versionamento não é
  removida.
- Alterações incompatíveis no formato pré-release não incrementam `CurrentVersion`; exigem reprovisionar todos os
  bancos, seeds e fixtures de desenvolvimento afetados.
- Serializers aceitam somente a versão `1` e continuam rejeitando versão diferente, JSON malformado e estrutura
  inválida.
- Não são criados leitores legados, upcasters ou migrations de JSON para formatos pré-release.
- O formato vigente no primeiro release suportado será congelado como a versão pública `1`. A partir desse marco,
  mudança incompatível exige nova versão e uma estratégia explícita de upgrade ou rejeição.
- O marco que encerra esta política deve ser registrado por nova decisão ou emenda explícita a este ADR; não pode
  ser inferido apenas porque um plano foi concluído.

Esta decisão abrange payloads de domínio persistidos, como `ServerOptions`, `RealmOptions`, authorization codes e
refresh tokens. Não se aplica a formatos criptográficos ou protocolares com versionamento próprio, como envelopes
de proteção, password hashes, digests e `session_state`.

## 3. Consequências

Uma linha antiga ainda marcada como versão `1` pode ser incompatível com o modelo corrente sem que o número da
versão revele isso. Essa limitação é aceita somente porque upgrades de dados pré-release não são suportados:
depois de qualquer corte incompatível, o ambiente deve ser reprovisionado antes de voltar a executar.

Planos pré-release deixam de reservar cadeias numéricas entre si. Seus gates verificam que os serializers
continuam em v1, atualizam seeds/fixtures para o formato corrente e documentam o reprovisionamento, mas não fazem
bump. Planos já concluídos permanecem como registro histórico e não precisam ser reescritos.

Os testes continuam cobrindo round-trip, estrutura obrigatória, ausência de propriedades removidas, JSON
malformado e rejeição de versões diferentes de `1`. Ao se aproximar o primeiro release, a revisão de prontidão
deve inventariar todos os payloads persistidos, congelar seus formatos correntes como v1 e definir a política de
upgrade para mudanças posteriores.
