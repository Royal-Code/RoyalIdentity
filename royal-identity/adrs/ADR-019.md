# 019. Hosts Server e Demo são composition roots independentes

## 1. Contexto

Os storages persistentes de Configuration e Operational e o módulo `UserAccounts` já possuem implementações
SQLite e PostgreSQL. O host `RoyalIdentity.Server` e o ambiente HTTP de testes ainda usam o storage in-memory
transitório, e a experiência de demonstração precisa continuar simples e descartável sem transformar SQLite em
provider produtivo.

Manter um único executável com seleção de provider misturaria responsabilidades de produção, demonstração e
provisionamento. Fazer o host de testes ou o Demo executar o `Program` do Server também deixaria a composição de
um ambiente dependente da de outro.

## 2. Decisão

- `RoyalIdentity.Server` é o host produtivo e usa exclusivamente PostgreSQL para Configuration, Operational e
  `UserAccounts`.
- `RoyalIdentity.Demo` é um executável web separado, fixo em SQLite in-memory e self-provisioned.
- Server e Demo não oferecem seletor de provider.
- Server, Demo e `Tests.Host` são composition roots independentes e não executam nem adaptam o entry point uns dos
  outros.
- O Server não executa migrations ou seed. Seu banco é provisionado externamente antes do processo web.
- Os hosts compartilham somente extensões provider-neutral pertencentes às suas camadas, inclusive a ordem
  protocolar crítica do RoyalIdentity; cada host conserva seu próprio shell, UI, tratamento de erros e
  antiforgery.

## 3. Consequências

- A execução local do Server exige PostgreSQL previamente provisionado.
- O Demo pode iniciar sem configuração de storage, mas seus dados são efêmeros e desaparecem a cada execução.
- Alguma duplicação de scaffolding web entre os executáveis é aceita para preservar a independência das
  composition roots.
- Novos providers ou orquestração não entram por um selector genérico do Server; exigem decisão e composição
  próprias.
